# sluiceULPmax

**Один проход по дампам. Сколько угодно подстрок. Диск — единственное, что осталось узким местом.**

Утилита для поиска по гигабайтам текстовых дампов (`url:login:pass`, комболисты, логи,
выгрузки). Читает файл ровно один раз и находит **все** запросы сразу, а потом раскладывает
найденное по файлам.

Написан на Rust. С интерфейсом в терминале — как у обычных CLI: пять экранов, кнопки, мышь.

```
                                         S L U I C E U L P
                           один проход · сколько угодно строк · твой диск

                         864 MB / 3.27 GB  ·  366 МБ/с  ·  найдено 30 210

                               wallet.example                    14 630
                               exchange.example                     10 780
                               store.example                          4 800
```

## Цифры

Файл 3.27 ГБ, 132 запроса, SATA SSD:

| | время | скорость |
|---|---:|---:|
| `grep -F -f` (132 шаблона) | ~9 мин | ~2 МБ/с |
| интерпретируемая реализация | 46.4 с | 70 МБ/с |
| **sluiceULPmax** | **8.4 с** | **417 МБ/с** |
| чистое чтение этого файла | 9.1 с | 384 МБ/с |

Полный поиск идёт **быстрее**, чем чтение того же файла без поиска: работа процессора
целиком спрятана под I/O.

## Почему так

1. **Параллельные блоки.** Файл режется на N диапазонов, границы выровнены по переводу
   строки — потоки не пересекаются и не синхронизируются вообще.
2. **`pread` вместо общего курсора.** Каждый поток читает по своему смещению; файл открыт
   с `FILE_FLAG_SEQUENTIAL_SCAN`, поэтому ОС агрессивнее читает вперёд.
3. **Фильтр по парам байт.** Таблица 64 КиБ + CSR-список кандидатов: проверка пары — одно
   чтение из L2. Aho-Corasick на 132 шаблонах выдыхается (его префильтр Teddy рассчитан
   на ≤64 шаблона, дальше остаётся голый DFA и 108 МБ/с против 139 у фильтра).
4. **Швы не теряются.** Недописанная на границе буфера строка переносится в следующий
   буфер и сканируется ровно один раз.
5. `-C target-cpu=native`, `lto = "fat"`, `codegen-units = 1`, `panic = "abort"`.

## Сборка

Нужен Rust 1.75+ и любой линкер: MSVC Build Tools или MinGW-w64.

```powershell
cargo build --release
.\target\release\sluiceULPmax.exe
```

На Windows двойной клик по `Launch.cmd` (лежит рядом) — запуск с паузой в конце.

## Интерфейс

Без аргументов открывается мастер: **источники → запросы → вывод → прогон → итоги**.

- `[+ файл]` / `[+ папка]` открывают проводник Windows;
- путь можно вставить или перетащить в окно терминала;
- в поле запросов работают `Ctrl+V`, стрелки, Home/End, Delete, кириллица;
- формат вывода: `url:login:pass`, `login:pass` или только счётчики;
- папка вывода выбирается тем же проводником;
- на прогоне — полоса, скорость и живая таблица лидеров.

| клавиша | действие |
|---|---|
| `Tab` / `←→` | перевести фокус по кнопкам |
| `Enter` | нажать кнопку в фокусе |
| `↑↓` | выбор в списке |
| `Esc` | назад / прервать прогон |
| `Ctrl+V` | вставить из буфера |
| `Q` / `Ctrl+C` | выход |

Мышь работает: клик по кнопке, по строке списка, по строке файлового браузера.

## Командная строка

```powershell
sluiceULPmax <файл|папка> "q1|q2" --count
sluiceULPmax <файл> --file списки.txt --format login --out hits
sluiceULPmax <файл> --file patterns.txt --caps
sluiceULPmax <файл> --bench io
sluiceULPmax <файл> --file patterns.txt --bench scan
```

| ключ | что делает |
|---|---|
| `--count` | только посчитать, строки не писать |
| `--tsv` | `count<TAB>pattern`, удобно для сверок |
| `--format url\|login\|raw` | вид выходной строки |
| `--out <папка>` | куда писать (по умолчанию `hits`) |
| `--threads auto\|N` | потоки (по умолчанию auto: замер диска и подбор) |
| `--chunk МБ` | буфер на поток (по умолчанию 32) |
| `--engine filter\|ac` | движок поиска (по умолчанию filter) |
| `--caps` | диагностика: ядра, скорость диска, рекомендация |
| `--bench io\|cpu:N\|scan` | замеры: диск / процессор / полный проход |
| `--no-ci` | учитывать регистр |
| `-V` | версия |

`--caps` выглядит так:

```
sluiceULPmax 1.0.0 — диагностика
  логических ядер   8
  файл              3.27 GB
  чтение (замер)    402 МБ/с
  сканер, 1 поток   127 МБ/с (на 132 запросах)
  нужно потоков     4
  рекомендуется     8
  (на холодном диске хватает 4, остальное — запас для горячего кэша)
```

## Формат вывода

```
url:login:pass     site.example/path/page:user123:pass123
login:pass         user123:pass123
```

Файлы кладутся по одному на запрос, имя = сам запрос.

## Ограничения

- литералы, без регулярок — это осознанно, регулярки убили бы скорость;
- поиск по подстроке: запрос `skins.example` поймает и `adskins.example`;
- один поток на диапазон файла; на NVMe упрётся в процессор (~1.1 ГБ/с на 8 потоках).

## Проверка

Счётчики по всем 132 запросам побайтово совпадают с эталонной реализацией на JS.
Швы, границы блоков и регистронезависимость проверены на файле 3.27 ГБ.
